# Build the Skyscraper — BACKEND (game server)

Frontend (3D client) lives at `../Build-the-skyscraper` (see its CLAUDE.md; `src/net.js` is the client end of this contract). Colyseus + Mongo, started from the Bowling Roll server and rewritten for this game: there is no boat/engine/race/spin server logic; the spin wheel is part of the client-authoritative save. The Daily / Playtime / Free rewards ARE server-authoritative (below).

- `npm start` (tsx watch, port 2567), `npm run build` (tsc -> `build/`), `npm test` (mocha + `@colyseus/testing`, Mongo faked via `__setPlayersForTest`, Bloxity's API faked via `__setFetchForTest`; tests share one booted server, `test/server.ts`). Node >= 22.
- One room, `world` (`src/rooms/WorldRoom.ts`, client calls `joinOrCreate("world", { token, devId, username, pfp, pose, loadout, avatar })`). Client-authoritative: the server only bounds/sanitises saves (`src/sanitize.ts`). `src/db.ts` degrades to "no persistence" when `MONGODB_URI` is unset/unreachable; guests are never saved. `/health` for Legion; `/monitor` and the playground are dev-only. SIGTERM drains through Colyseus' graceful shutdown (rooms disconnect, `onDispose` flushes the queued Bloxity reports); the Docker image runs as a non-root user.
- **Identity (Bloxity rule: never trust a client id)** (`src/auth.ts`): `onAuth` verifies the join option `token` (`Legion.SDK.auth.getToken()`) with `POST {BLOXITY_API_URL|https://api.bloxity.io}/v1/auth/game-token/verify` (`Authorization: Bearer`, body `{ gameSlug: "build-the-skyscraper" }`) and uses ONLY the returned `user._id` (display name / pfp come from the same answer). A missing, refused (401) or unverifiable token is a guest: nothing is loaded or saved and a client-sent `userId` is ignored. `devId` (`dev-xxxx`, per-browser, sent by the client in local dev when there is no SDK) is honoured only when `NODE_ENV !== "production"`. No `identify` message: when a guest signs in mid-session the client saves, then reloads with `?roomId=` and rejoins the same room under its token (the new account loads its save, or adopts the browser's guest progress on `noProgress`). A second live session on the same account is evicted. Roster `uid` is the account id Bloxity chat's `userId` matches.
- Messages client -> server: `saveProgress` (the whole snapshot, debounced client-side), `pose`, `loadout`, `setAvatar`, `emote`, `build`, `claimReward`, `rewardsRefresh`, `claimOffline`, `claimInvite`, `inviteRefresh`, `invited`. Server -> everyone: `built`. Server -> client (private): `progress` (the saved doc, sanitized, + `serverTime`), `noProgress` (new account, guest, or no database: the client keeps its state and saves it), `serverError` (the save could not be read: saving stays off so it is never overwritten), `leaderboard`. Saves are ignored until the session's load has answered (`loaded`) and are written one at a time per session so they land in order.
- Saved progress shape (`PlayerDoc` in `src/db.ts`, bounds in `src/sanitize.ts` + `src/constants.ts`; the client's `SAVED` list in `stats.js`): `cash`, `strength`, `speed`, `totalBlocks`, `buildings`, `bag`, `upgrades { id: level }`, `passes { id: true }`, `gymOwned { tier: true }`, `daily { day: "YYYY-MM-DD", streak }`, `giftIn`, `playtime`, `tower { n, floors, blocks }`, `rankSeen`, `gear { owned { id: true }, on }` (the worn piece must be owned), `pets [{ uid, id, tier }]`, `petEq [uid]` (owned only), `petSeen { id: true }`, `petUid`, `spins { normal, golden, pity }`, `petSlots` (extra pet slots bought, max `PET_SLOTS_BOUGHT_MAX`), `timed [{ stat cash|strength|speed, mult, left }]` (running reward boosts, `sanitizeTimed`), `goals { kind, need, have, reward, done, day, today, seen }` (the client's Goals tracker, `sanitizeGoals`: slug kind, bounded numbers; junk leaves the field alone), `rewards`, `lastSeen` and `offlineSecs` are written ONLY by the server (never taken from a save). Only the fields a save carries are written, so a partial save never wipes the rest.
- Rewards (`src/rewards.ts`, `test/Rewards.test.ts`; client `rewards.js` / `rewardsUi.js`, `REWARDS` in its config.js; `DAILY_DAYS` / `PLAY_TIERS_MIN` here must match `REWARDS.daily.length` / `REWARDS.play[].at`): server-authoritative on the server's UTC days for signed-in players with a database (guests and no-DB sessions get nothing: their browser keeps the same rules). Doc field `rewards { streak, last (UTC day of the last daily claim), playDay, playSec (connected seconds that day), playClaimed[], free }`. On load (before `progress`) the client gets `rewards` { daily: { day (0-based next), canClaim, streak, nextAt }, play: { sec, claimed }, free, serverTime }. `claimReward` { kind: daily | play (tier) | free } answers `rewardResult` { ok, kind, day? | tier?, reason?: none | busy | claimed | early | tier | kind | save, view } — ok only once the claim is stored (one claim at a time per session); the client grants the prize then. Daily: claimable once per UTC day, the day after the last claim continues the streak, a missed day (or a finished week) starts at day 1. Playtime resets at UTC midnight and rides along with every save and the leave stamp. `rewardsRefresh` re-sends `rewards` (the client asks after midnight).
- **Offline rewards / "While You Were Away"** (`src/offline.ts`, `test/Offline.test.ts`; client `offline.js` / `offlineUi.js`, `OFFLINE` in its config.js; `OFFLINE_MIN_S` / `OFFLINE_MAX_S` here must match `OFFLINE.min` / `OFFLINE.max`): server-authoritative for signed-in players with a database (guests and no-DB sessions: the browser keeps its own `lastSeen`, same rules). The SERVER measures the time away on its clock: `lastSeen` is stamped on every save, on leave and on load and is NEVER taken from a save (nor is `offlineSecs`). On load (`loadOffline`, before `progress`) `away = now - lastSeen` (< `OFFLINE_MIN_S` = nothing, capped at `OFFLINE_MAX_S` = 24 h) is added to the unclaimed `offlineSecs` (capped again) and stored with the new `lastSeen` (conditional on the `lastSeen` read, so two pods never both add one absence), then the client gets `offline` { secs, max } (secs 0 = no popup). `claimOffline` answers `offlineResult` { ok, secs?, reason?: none | busy | claimed | save }: ok only once `offlineSecs` is zeroed (conditional on the exact stored value, so a double claim pays once); the client then grants Strength + Speed for `secs` (what the time is worth lives in the client's `OFFLINE`: minutes x per-minute rate x the best unlocked gym pad x passes, never boosts or pets, never Gems).
- **Invite Friends** (`src/invite.ts`, `test/Invite.test.ts`; client `invite.js`, config `INVITE`): a friend counts for their inviter only once they ACTUALLY PLAY. A signed-in NEW player (no save, or < `INVITE_NEW_PLAYTIME_MAX` s saved) who joins through the inviter's link (join option `ref` = the inviter's account id, from `?ref=`) or after a direct Bloxity invite (`invited { friendId }` -> the inviter's `invitesSent`) gets, once ever (conditional write on `invitedBy`), `invitedBy` + `welcome: "ready"`; the inviter is NOT credited yet (that friend is `pending`). When the friend's saved progress reaches `INVITE_ACTIVE` (`playtime` >= 180 s AND `totalBlocks` >= 300) the inviter's `invites` goes up by one, once per friend (`inviteCredited`, conditional write, so two pods never both credit); an inviter in the same room hears it live (`friendJoined { name }` + a fresh `invite` view), others on `inviteRefresh` / next join. Guests, veterans, unknown refs and self-invites never link; `invites` is capped at `INVITES_MAX`. Messages: `claimInvite { id: "welcome" | tier index }` -> `inviteResult { ok, id, reason?: guest | loading | locked | save, ...view }` (ok only once stored, then the client grants the prize), `inviteRefresh`, `invited`; server -> client `invite` view `{ invites, pending, claimed[], welcome, tiers[] (= `INVITE_TIERS`), invitedBy (name), active, need { playtime, blocks } }`, `invitedBy { name }` (welcome gift ready). Doc fields `invites`, `inviteClaimed`, `welcome`, `invitesSent`, `invitedBy`, `inviteCredited` are written ONLY by the server (never taken from a save). Prizes live in the client (`INVITE` in config.js): cash scaled by buildings finished, timed boosts, free upgrade levels, eggs and Robot Gear, never Gems. There are no worker bots and no Crew any more (the saved `crew` field is gone; an old save's is ignored).
- **Shared tower** (`src/tower.ts`, `test/Tower.test.ts`; schema `WorldState.tower` = `TowerState`): ONE authoritative tower per room (up to `ROOM_MAX_CLIENTS` = 50 players), displayed by every client (client `tower.js` `sync`). `TowerRules` holds the rules over the schema object (so every change syncs through Colyseus): `building` -> (last floor filled) `celebrate` (`INSIDE_SECONDS` = the client's `INSIDE.time`, the lobby is open) -> `sinking` -> building `n + 1` `NEXT_BUILDING_DELAY_S` (8.725 s: sinkTime + the Next Building reel's hold) after the sinking started. Building n has `buildingFloors(n)` floors (`BUILDING_SCALE` copy); **each floor's size is set when it starts, from the bags of the room's active builders** (`floorNeed(n, floor, roomTrip)`: `floorTrips(n)` = tripsBase + n * tripsPer (max tripsMax) x the summed `trip`s of everyone who built in the last `BUILDING_SCALE.active` s x (1 + floor * floorGrowth), never under `floorMin` = minBase * minGrowth^n), so a floor takes a minute or two whoever is in the room and a new player's bag is a visible chunk of it; `tick` shrinks a started floor when the room gets weaker (never below what is on it + 1, so it never sticks). Its LOOK is the client's seeded `pickBuilding(n)`, so only `n, floors, blocks, need (the floor's size), placed (blocks on this building), phase, phaseAt (server ms), seeded` travel. Clients report `build { blocks, trip }` (the blocks they placed, batched ~4/s, and `trip` = blocks one full bag of theirs places, bounded by `TRIP_MAX`; `WorldRoom.trips` keeps each session's bag and last build time; token bucket `BUILD_BUCKET`; rolls floors over, each new floor sized to the room then, may finish the building); there is no ack, the new state arrives through the schema. When the last floor fills, everyone gets `built { n, builders: [{ id, name, blocks }] }` (top `BUILDERS_TOP` contributors on that building; `id` = account id or sessionId) for the finale. The room clock (`TOWER_TICK_MS`) advances the timeline. **Seeding**: a fresh room's tower starts from the first loaded player's stored `tower` (signed-in), else from the join option `tower` (their browser save), else building 0; `seeded` flips true and clients wait for it before building the world; later players adopt the room's tower. The room's tower is in memory: it lives as long as the room (players' saves keep the last `tower` they saw and seed the next room). Worker bots are cosmetic in a connected client (they add no blocks); rewards for a finished floor / building stay per player and client-side.
- Roster (`PlayerState`, `src/rooms/schema/WorldState.ts`, relayed bounded by `src/presence.ts`, `test/Presence.test.ts`): `username`, `signedIn`, `pfp` (http(s) only), `uid`, `x`/`y`/`z`/`yaw`/`speed`/`act` (`pose` ~10/s; `act` "", "bench", "chute" (under a parachute: the others draw the canopy) "impact" (a Robot Gear superhero landing: the others play its crouch, cracks and rubble), "fly" (thrusters on), "climb" (Spider Arms on the tower wall), "vehicle" (a transformer's vehicle form on the ground) or "jet" (the Jet Transformer in the air); with `gear` the others wear the piece and play these), `rank`/`strength`/`gear` (`loadout`: name tag, muscle), `avatar`, `emote`/`emoteAt`. The avatar is Bloxity equipped IDS ONLY: `setAvatar` takes JSON `{ equipped, proportions }` and the server REBUILDS it from an allowlist of slot keys (`AVATAR_SLOT_KEYS`) and proportion fields, so no URL or extra field can ride along; clients derive skin/part URLs from the ids. `emote` { id } (24-hex Bloxity emote id, "" stops): Bloxity sends `play_emote` only to the picker, so the picker's client relays it here and `emoteAt` (server clock, ms) is what makes the others replay it. Chat bubbles need nothing here: Bloxity's `chat.onMessage` reaches every client, which maps `userId` to a roster `uid`.
- In-world leaderboards (`src/leaderboard.ts`, `test/Leaderboard.test.ts`): top `LEADERBOARD_SIZE` saved players per board `strength`, `speed`, `blocks` (doc `totalBlocks`), `cash`, `buildings`, `playtime` (`LEADERBOARD_FIELDS`), read with find/sort/limit into one process-wide cache refreshed at most every `LEADERBOARD_EVERY_MS`; each player's own rank = countDocuments(field > theirs) + 1 (null for guests / no score). `leaderboard` { boards: { key: [{ name, value }] }, ranks: { key: n | null } } is sent after each load and to everyone every `LEADERBOARD_EVERY_MS` (room clock). `connectDb` creates a descending index per field.
- Bloxity leaderboards + stats (`src/boxity.ts`, `test/Boxity.test.ts`; constants `BOXITY_BOARDS` / `BOXITY_STATS`, the client defines the same boards in `config.js` `BLOXITY_BOARDS`): after each save and on load the player's stored values are queued and sent every `BOXITY_FLUSH_MS`, only what changed: boards via `POST {api}/v1/leaderboards/hosted/{BLOXITY_GAME_ID}/report` (declared with the first accepted call), stats via `POST {api}/v1/games/{BLOXITY_GAME_ID}/stats` (definitions on every call, values over the platform ceilings left out), identities `legion_<id>`, dev ids never. Needs the injected `BLOXITY_REPORT_TOKEN` + `BLOXITY_GAME_ID`; without them (local dev, tests) nothing is sent. The game is client-authoritative, so these are the saved (bounded) numbers, not server-simulated ones.
- Open rooms (Bloxity game page "Open Rooms" list + its Join button = `?roomId=`): a hosted server must run the room reporter, it is NOT automatic. `src/legion-room-reporter.ts` (`installRoomReporter()` in `src/index.ts` after `listen`, `test/RoomReporter.test.ts`) POSTs this pod's live rooms (`matchMaker.query`: `colyseusRoomId, name, clients, maxClients, locked, private, started, metadata`) plus `podName` and `players` to `${MATCHMAKER_REPORT_URL}/${BLOXITY_GAME_ID}/rooms` with `Authorization: Bearer ${BLOXITY_REPORT_TOKEN}` every 2 s (4 s timeout, failures ignored; private rooms are never listed). It is a no-op unless `BLOXITY_REPORT_TOKEN` and `MATCHMAKER_REPORT_URL` are set (injected by Legion hosting; `POD_NAME` names the pod), so local dev and tests send nothing. Without it the game page shows no rooms. One catalogue row, so no `mode` metadata is needed. The client joins `?roomId=` first (resolved through `GET {playUrl}/v1/dir/<id>/list`, never a bare joinById) and calls `updateRoom`. `maxClients` = `ROOM_MAX_CLIENTS` (2-100 for party play).
- `src/constants.ts` bounds must cover the client's `src/config.js` (catalog ids match `ID_PATTERN`; ranks `RANK_MAX`). A contract change goes in both projects.
- CI/CD: `.github/workflows/deploy.yml` tests on PRs and pushes to `main`/`dev`; pushes also build+push a GHCR image and deploy to Bloxity Legion (`main` = prod, `dev` = dev), sending `roomSize` = `ROOM_MAX_CLIENTS` read from `src/constants.ts` (keep it 2-100 for party play; no `seatCap`: the matchmaker sizes pods). The game ID is the slug `build-the-skyscraper` (hardcoded default in the workflow; `LEGION_GAME_ID` var/secret only overrides it). Needs secret `LEGION_DEPLOY_TOKEN`.
